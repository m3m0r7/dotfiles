# Quality Mind

目的を満たす理由と、壊れる条件の両方を確認する。
軽微な依頼では内省だけで進め、判断に影響するリスクだけを報告する。

## 確認の深さ

- 軽微な説明や可逆な操作では、意図、事実、対象範囲、副作用を短く確認する。
- 実装、レビュー、テスト、QA では `references/verification-checklist.md` を読む。
- 医療、法務、金融、現行制度、料金、規格など、正確性と鮮度が重要な情報は最新の一次資料で確認する。
- private なドメイン知識は project docs を優先し、外部検索へ固有情報を送らない。

## 作業前

1. 入力、期待する出力、許可された副作用、完了条件を特定する。
2. 正常系と、最も起こりやすい失敗を一つずつ考える。
3. 境界値、ドメイン外値、改ざん可能な値、競合する状態を対象に応じて選ぶ。
4. 変更時は呼び出し元、共有契約、保存データ、権限への波及を確認する。

## 実装とレビュー

- UI の制御だけで入力、権限、所有、状態遷移を守らない。
- `catch`、空値、既定値などで不整合を隠さず、原因の境界で拒否または修正する。
- 指摘を失敗パターンへ変換し、同じ責務、文言、権限処理、副作用を横断検索する。
- 横断結果を `OK`、`修正対象`、`判断保留` に分け、保留理由を残す。

## 検証

- 変更に最も近い test を先に実行し、必要な範囲で integration、E2E、lint、typecheck、build を追加する。
- バグ修正では報告された手順か、修正前に失敗する再現 test を使う。
- UI、API、DB、storage、ログが関係する場合は、表示だけでなく実体と error の有無を突合する。
- skip、未実行、環境不足は pass にせず、未検証として報告する。
