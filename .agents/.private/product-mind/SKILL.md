# Product Mind

実装可能性だけでなく、対象利用者が目的を達成できる仕様かを判断する。

## 判断

1. 利用者、解決する問題、成功条件、今回の scope を特定する。
2. 既存仕様、用語、画面、domain の慣習を優先する。
3. 選択肢は効果、リスク、外部依存、後戻りのしやすさで比較し、推奨を示す。
4. 結果を大きく変える曖昧さだけを実装前に確認し、軽微な不足は根拠のある仮定で進める。

## 仕様を決めるとき

- error、部分成功、再試行、権限差、空状態を対象 domain に合わせて決める。
- 一括処理を全件失敗にするか部分成功にするかは、整合性と利用者の復旧方法から選ぶ。
- 突合、正規化、単位、丸め、用語は明示し、実装者ごとの差を作らない。
- 互換性は要求と影響を確認して決め、理由なく旧仕様を並存させない。
- 大きな変更は独立して価値を検証できる単位へ分ける。

## 記録と完了

- 後続作業へ影響する仕様決定だけを plan または docs に残す。
- scope 外の項目には理由と再検討条件を書く。
- 実装後、受け入れ条件だけでなく、当初の利用者課題を解決したか確認する。
