# Reporting Mind

報告は「やったことの記録」ではなく「読み手が次の行動を決められる材料」。読み手を設定してから書くための skill。

## 基本形

- 結論を先頭に書く。まず「何が起きたか / 何をしたか / 今どういう状態か」を 1〜3 文で言い切り、詳細はその後ろに置く。
- 経営層・非エンジニアへそのまま転送できるエグゼクティブサマリを冒頭に置く。技術詳細はセクションを分ける。
- 作業ログ(「〜を試しました」「〜で苦労しました」)や定型句を本文に書かない。読み手に必要な情報だけを残す。
- ユーザーへの質問はナンバリングし、番号だけで回答できる形にする。1 つの質問に 1 つの論点。

## バグ・障害の報告

必ず次の 3 点をセットで含める。どれかが欠けた「直りました」報告はしない。

1. **根本原因**: 症状ではなく原因。どのコード・どの前提が問題だったか。
2. **混入時期**: いつ・どの変更で入ったか(必要なら履歴・bisect で特定)。
3. **検出漏れの理由**: なぜ既存のテスト・確認で捕まらなかったか。再発防止に何を足したか。

加えて、修正のエビデンス(再現手順の before / after、スクリーンショット)を添える。再現できなかった場合は正直にそう書く。

## 複数課題の進捗

- 「課題 × 状態 × 確認方法」のマトリクス(表)で示す。文章の羅列にしない。
- 状態は「修正済み・確認済み / 修正済み・未確認 / 未対応 / 対象外」を区別する。「たぶん直った」を「done」と書かない。
- 人間の確認が必要な項目(実機での目視、判断が要る仕様)を、自動で確認済みの項目と分けて提示する。
- 未検証のリスク・スコープ外にしたものを最後に明示する。

## エビデンスの作法

- スクリーンショットは対象箇所が確実に写っている状態で撮る(必要ならスクロール・ウィンドウ幅調整)。撮っただけで対象が写っていないものはエビデンスではない。
- 転送用途では枚数を絞る(要点が伝わる 2 枚程度に構成し、番号付きの説明を添える)。
- ファイル名・保存場所は後から探せる形にする(観点・ケースが分かる名前、プロジェクトの定位置)。

## PR / MR の本文

- その PR の実装仕様を説明するものにする。何を・なぜ・どう変えたか、影響範囲、確認方法。必要なら図解(mermaid 等、プロジェクトの慣習に従う)を含める。
- レビュー往復で実装が変わったら本文も更新する。本文と実装を食い違ったままにしない。
- 作成・更新したら PR / MR の URL をユーザーに提示する。
- レビューコメントへの返信や PR への書き込みは、外部に見える発信なので、投稿前に内容をユーザーに見せる(明示的に任されている場合を除く)。

## 引き継ぎ

- 長期タスクの中断・セッション終了時は、plan / handoff md に「完了したこと・残タスク・次の一手・ハマりどころ」を更新してから終える。次の担当(人間でもエージェントでも)が文脈なしで再開できることが基準。
